# Анализ архитектурных проблем

1. Сервис `core-app` обновляет информацию по продуктам партнёрских страховых
   компаний раз в 15 минут, а сервис `ins-comp-settlement` обновляет эту же
   информацию раз в сутки. Это приводит к тому, что в различные моменты времени
   информация по продуктам может различаться между сервисами.
2. Каждый сервис хранит снимок данных по продуктам у себя, в своей БД. Это
   приводит к следующим проблемам:
   - При расширении структуры данных по продуктам необходимо будет обновлять
     схемы СУБД сервисов `core-db` и `ins-comp-settlement-db`.
   - Если у партнёрской страховой компании удалился какой-то страховой продукт,
     то информация об этом обновится через какое-то время. Пока она не
     обновится, за этот промежуток времени могут оформляться страховки по уже
     не существующим или не действующим тарифам.
3. У cервиса `ins-product-aggregator` нет собственной БД для хранения данных по
   продуктам, нет кэша. Поэтому сервис может создавать лишнюю нагрузку на API
   сервисов партнёрских страховых компаний.
4. Сервис `ins-comp-settlement` раз в сутки запрашивает у сервиса `core-app`
   информацию по всем оформленным страховкам. За сутки их может накопиться
   большое количество, поэтому запрос на получение информации по всем
   оформленным страховкам может быть тяжёлым и создавать нагрузку на
   `core-app`. Это может создавать проблемы пользователям из других часовых
   поясов, которые могут работать с системой во время процесса получения и
   обработки информации по оформленным страховкам.
5. Неясен процесс обновления данных по клиентам: обновлением могут заниматься
   как и личный кабинет пользователя, так и сервис `core-app`. Нет чётко
   описанных условий необходимости обновления данных клиента в процессе
   оформления страховки. Такой процесс может быть источником ошибок.

# Анализ основных событий системы

1. **Создание пользователя**: регистрация пользователя. Пользователь может быть
   как корпоративным и быть зарегистрированным через стыковочное API, так и
   частным, который регистрируется через Личный Кабинет.
2. **Изменение пользователя**: изменение данных пользователя может быть
   инициировано как через стыковочное API со стороны партнёра, так и со стороны
   Личного Кабинета.
3. **Удаление (отключение) пользователя**: отключение пользователя (удаление)
   может быть инициировано как через стыковочное API со стороны партнёра, так и
   со стороны Личного Кабинета.
4. **Оформление страховки**: на пользователя оформляется страховка, после
   проведения оплаты.
5. **Открытие страхового продукта**, **Обновление страхового продукта**,
   **Закрытие страхового продукта**: происходит во время обновления и сверки
   сведений о страховых продуктах партнёрских страховых компаний.
